# Elementary types

<SpecLink
  schema="ethdebug/format/type/elementary"
  href="/spec/category/elementary-types"
/>

Elementary types are atomic—they don't contain other types. These form the
building blocks that complex types compose.

## Numeric types

Unsigned integers, signed integers, and fixed-point numbers all use the
`number` kind. A `number` type has no width. The type says what the value
is; the value's pointer says where its bytes are, and so how many bytes
there are.

<SchemaExample
  schema="type/elementary/number"
  href="/spec/type/elementary/number"
>
  {`{ "kind": "number" }`}
</SchemaExample>

The optional `label` field gives the type as the language spells it:

<SchemaExample
  schema="type/elementary/number"
  href="/spec/type/elementary/number"
>
  {`{ "kind": "number", "label": "uint8" }`}
</SchemaExample>

### Signed integers

Signed integers use two's complement representation:

<SchemaExample
  schema="type/elementary/number"
  href="/spec/type/elementary/number"
>
  {`{ "kind": "number", "signed": true }`}
</SchemaExample>

When `signed` is omitted, the number is unsigned.

### Fixed-point numbers

Fixed-point decimals specify the number of decimal places:

<SchemaExample
  schema="type/elementary/number"
  href="/spec/type/elementary/number"
>
  {`{ "kind": "number", "signed": true, "places": 18 }`}
</SchemaExample>

The number is the integer value of its bytes divided by `10**places`. When
`places` is omitted, the number is an integer.

## Address type

Addresses represent Ethereum addresses:

<SchemaExample
  schema="type/elementary/address"
  href="/spec/type/elementary/address"
>
  {`{ "kind": "address" }`}
</SchemaExample>

In Solidity, `address payable` is distinguished by the `payable`
field:

<SchemaExample
  schema="type/elementary/address"
  href="/spec/type/elementary/address"
>
  {`{ "kind": "address", "payable": true }`}
</SchemaExample>

When `payable` is omitted, the address's payability is unknown.

## Boolean type

Booleans represent true/false values:

<SchemaExample schema="type/elementary/bool" href="/spec/type/elementary/bool">
  {`{ "kind": "bool" }`}
</SchemaExample>

The value 0 is false and the value 1 is true. Any other value is invalid.

## Byte types

Byte strings use the `bytes` kind:

<SchemaExample
  schema="type/elementary/bytes"
  href="/spec/type/elementary/bytes"
>
  {`{ "kind": "bytes" }`}
</SchemaExample>

A `bytes` type has no size. Fixed-size and dynamic byte strings both use
this kind; the value's pointer says how many bytes there are. The `label`
field can keep the language's spelling:

<SchemaExample
  schema="type/elementary/bytes"
  href="/spec/type/elementary/bytes"
>
  {`{ "kind": "bytes", "label": "bytes32" }`}
</SchemaExample>

## String type

Strings represent UTF-8 encoded text:

<SchemaExample
  schema="type/elementary/string"
  href="/spec/type/elementary/string"
>
  {`{ "kind": "string" }`}
</SchemaExample>

Languages that treat strings as character arrays may choose to represent them
as `array` types instead.

## Enum type

Enums represent a fixed set of named values:

<SchemaExample schema="type/elementary/enum" href="/spec/type/elementary/enum">
  {`{
  "kind": "enum",
  "definition": {
    "name": "Status"
  },
  "values": ["Pending", "Active", "Completed"]
}`}
</SchemaExample>

The `values` field lists all possible values in order. The value is read
as an unsigned integer `i`, which selects `values[i]`.

## Flags type

Flags represent a set of named flags:

<SchemaExample
  schema="type/elementary/flags"
  href="/spec/type/elementary/flags"
>
  {`{
  "kind": "flags",
  "definition": {
    "name": "Permissions"
  },
  "values": ["READ", "WRITE", "EXECUTE"]
}`}
</SchemaExample>

The value is read as an unsigned integer. If bit `i` is set, `values[i]` is
in the set. The value 0 is the empty set.

## Contract type

Contract types are `address` types with a `definition` field. The
definition names the contract:

<SchemaExample
  schema="type/elementary/address"
  href="/spec/type/elementary/address"
>
  {`{
  "kind": "address",
  "definition": {
    "name": "MyToken"
  }
}`}
</SchemaExample>

The value is an address, but the type carries additional semantic
information about which contract interface applies. A definition may mark
the contract as a library or an interface with the `library` or
`interface` field.

## User-defined types with definitions

Some elementary types (particularly enums) are defined in source code. These
include a `definition` field:

<SchemaExample
  schema="type/elementary/enum"
  href="/spec/type/elementary/enum"
  title="Enum with source location"
>
  {`{
  "kind": "enum",
  "definition": {
    "name": "OrderStatus",
    "location": {
      "source": { "id": 42 },
      "range": {
        "offset": 150,
        "length": 85
      }
    }
  },
  "values": ["Created", "Filled", "Cancelled"]
}`}
</SchemaExample>

The `definition` field can include:

- `name`: The identifier used in source code
- `location`: A source range where the type is defined
